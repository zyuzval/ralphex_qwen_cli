## 1. Философия

### Одна роль — один агент

Агент работает хорошо ровно тогда, когда у него одна ответственность. Не «делай код лучше», а «найди проблемы в этом модуле и задокументируй их». Не «разберись с тестами», а «запусти тесты, собери упавшие, верни структурированный отчёт».

Чем шире роль — тем непредсказуемее поведение. Агент начинает принимать решения которые ему не делегировали, пропускает то что казалось очевидным, и его сложно отлаживать потому что непонятно где именно он свернул не туда.

### Скилл — это знание, агент — это роль

Скилл отвечает на вопрос «что знать». Агент отвечает на вопрос «что делать и в каких рамках».

Скилл можно переиспользовать между агентами. Знание о том как писать тесты (TEST-PATTERNS.md) нужно и TestWriterAgent, и FixAgent. Знание о коммит-конвенциях нужно и CommitAgent, и PRAgent.

Агент переиспользовать нельзя — у него конкретная роль в конкретном контексте.

### Координатор — не исполнитель

Если агент координирует других агентов, он не должен сам исполнять задачи. Его работа — принять решение, делегировать, получить результат, обработать. Как только координатор начинает «немного помогать» субагентам — схема разваливается.

## 2. Когда нужен агент, когда скилл

### Нужен агент если:
- Задача повторяется регулярно и имеет чёткий вход/выход
- Задача требует последовательности шагов с промежуточными проверками
- Разные люди (или агенты) должны делать одно и то же одинаково
- Задача занимает больше 15 минут и требует концентрации на одном
- Ошибка в задаче дорого стоит и нужна воспроизводимость

### Нужен скилл если:
- Это знание которое нужно перед работой, а не во время
- Это политика или соглашение («всегда делай X перед Y»)
- Это паттерны и антипаттерны которые агент должен распознавать
- Это описание предметной области (форматы данных, структуры, термины)
- Информация не меняется между запусками

### Не нужен ни агент, ни скилл если:
- Задача разовая и не повторится
- Человек справляется быстрее чем написать агента
- Нет чёткого критерия «сделано правильно»

## 3. Анатомия агента

Каждый AGENT.md содержит семь секций. Все обязательны.

```
# [Имя]Agent

## Роль (одна строка)
Что делает этот агент — ёмко и конкретно.

## Вход
Что агент получает для работы. Формат, источник, обязательность.

## Выход
Что агент производит. Формат, куда пишет, структура.

## Скиллы
Какие файлы читать в начале работы (в порядке важности).

## Правила
Что агент ОБЯЗАН делать. Не рекомендации — требования.

## Запреты
Что агент НЕ ДЕЛАЕТ никогда. Границы роли.

## Взаимодействие
С кем работает: кто запускает агента, кому он отдаёт результат.
```

### Почему все секции обязательны

**Роль** — без неё агент дрейфует в соседние задачи.

**Вход** — без него агент начинает искать данные сам и находит не то.

**Выход** — без него результат непредсказуем по формату.

**Скиллы** — без них агент работает из общих знаний, а не из контекста проекта.

**Правила** — без них агент оптимизирует что считает нужным.

**Запреты** — самая важная секция. Агент должен явно знать что НЕ делать. Без запретов граница роли размыта и агент «немного помогает» соседям.

**Взаимодействие** — без него агент не знает кому докладывать и в каком формате.

## 4. Анатомия скилла

Скилл — это markdown-файл который агент читает как контекст перед работой. Не инструкция по шагам — база знаний.

```
# [Название] — [что описывает]

## Контекст
Почему это знание важно. Что происходит без него.

## Паттерны (что делать правильно)
Конкретные примеры с кодом или структурой.

## Антипаттерны (что не делать)
Конкретные примеры того что выглядит правильно но неправильно.

## Правила принятия решений
Если X → делай Y. Дерево решений для типичных ситуаций.

## Примеры из проекта
Реальные примеры из кодовой базы. Не абстрактные.
```

### Принципы написания скилла

**Конкретность важнее полноты.** Лучше три точных правила чем двадцать расплывчатых.

**Примеры важнее описаний.** «Используй атомарные записи» хуже чем показать код атомарной записи.

**Антипаттерны обязательны.** Агент должен знать не только как правильно, но и как выглядит неправильно — потому что неправильное часто выглядит правдоподобно.

**Проектный контекст важнее общих знаний.** Агент уже знает общие принципы программирования. Скилл нужен для специфики именно этого проекта.

## 5. Как агенты взаимодействуют

### Три модели координации

**Цепочка (Pipeline)**
```
ReviewAgent → FixAgent → CommitAgent
```
Каждый агент берёт выход предыдущего как вход. Простая модель, легко отлаживать. Минус: падение одного останавливает всё.

**Звезда (Hub-and-Spoke)**
```
         ReviewAgent
        /
Coordinator → FixAgent
        \
         CommitAgent
```
Координатор принимает решения, субагенты исполняют. Гибко, но координатор становится узким местом.

**Параллельная**
```
Coordinator → [ReviewAgent, LinterAgent, TestWriterAgent] → агрегация
```
Несколько агентов работают независимо над разными аспектами, координатор агрегирует результаты. Быстро, но сложнее синхронизировать.

### Формат передачи данных

Агенты общаются через файлы или MCP, не через прямые вызовы. Это ключевое решение: агент не знает кто его запустил и кто будет читать его вывод. Он просто пишет в условленное место.

```
# Правило передачи данных
Агент A пишет → [файл/MCP] → Агент B читает
                                
Не: Агент A вызывает Агент B напрямую
```

Формат вывода всегда JSON или структурированный Markdown — что угодно кроме произвольного текста. Произвольный текст невозможно надёжно распарсить.

## 6. Шаблон агента

```markdown
# [Имя]Agent

## Роль
[Одно предложение. Глагол + объект + ограничение.]
Пример: "Анализирует код модуля на наличие проблем и записывает их в структурированный отчёт. Не исправляет."

## Вход

| Параметр | Тип | Источник | Обязателен |
|----------|-----|----------|------------|
| target | путь к файлу/директории | аргумент запуска | да |
| context | краткое описание задачи | аргумент запуска | нет |

## Выход

**Файл:** `docs/[тип]/[дата]-[имя].md`  
**Формат:** Markdown с фиксированной структурой (см. скилл OUTPUT-FORMAT.md)  
**При ошибке:** записать в тот же файл секцию `## Errors` с описанием

## Скиллы

Читать в начале каждой сессии в этом порядке:
1. `BOOT.md` — контекст проекта
2. `skills/REVIEW-PATTERNS.md` — паттерны и антипаттерны
3. `skills/OUTPUT-FORMAT.md` — формат вывода

## Правила

- Начинай с чтения скиллов, затем целевого файла
- Каждая найденная проблема получает severity: Critical / High / Medium / Low
- Минимум одно предложение обоснования для каждой проблемы
- Если файл не существует — записать ошибку в выход, не завершать работу
- Документировать всё найденное, даже если кажется незначительным

## Запреты

- НЕ исправлять код — только документировать
- НЕ открывать файлы вне target директории
- НЕ делать предположений о намерениях автора кода
- НЕ пропускать проблемы потому что «автор наверное знает»
- НЕ обновлять WAL.md — это задача координатора

## Взаимодействие

**Запускает:** Coordinator или человек напрямую  
**Отдаёт результат:** пишет файл в docs/reviews/, уведомляет через MCP (update_session_status)  
**Не взаимодействует напрямую с:** FixAgent, CommitAgent
```

## 7. Шаблон скилла

```markdown
# [Название]

## Для кого
[Имя]Agent — [одна строка зачем этот скилл этому агенту]

## Контекст
Почему это знание критично. Что ломается без него.

## Правила (применять всегда)

### Правило 1: [Название]
[Описание]

✅ Правильно:
[пример кода или структуры]

❌ Неправильно:
[пример того что выглядит правдоподобно но неверно]

### Правило 2: [Название]
...

## Решения по ситуациям

| Ситуация | Решение |
|----------|---------|
| Файл не найден | Записать в секцию Errors, продолжить |
| Неоднозначный случай | Документировать как Medium, добавить пометку REVIEW |
| Конфликт с другим правилом | Приоритет у более строгого |

## Примеры из этого проекта

### Хороший пример
[Реальный код/структура из проекта]

### Плохой пример (реально встречался)
[Реальный антипаттерн из проекта с объяснением почему плохо]

## Что НЕ входит в этот скилл
[Явно обозначь границы — что агент не должен делать на основе этого скилла]
```

## 8. Области применения

### Код
| Агент | Задача | Скиллы |
|-------|--------|--------|
| ReviewAgent | Поиск проблем | REVIEW-PATTERNS, CODE-QUALITY |
| FixAgent | Применение исправлений | FIX-PATTERNS, TESTING |
| RefactorAgent | Улучшение структуры без изменения поведения | REFACTOR-PATTERNS |
| LinterAgent | Статический анализ + форматирование | LINT-RULES |
| TestWriterAgent | Написание тестов по существующему коду | TEST-PATTERNS |
| DebugAgent | Диагностика упавших тестов/ошибок | DEBUG-PATTERNS |

### Процесс
| Агент | Задача | Скиллы |
|-------|--------|--------|
| CommitAgent | Подготовка и создание коммита | COMMIT-CONVENTIONS |
| PRAgent | Описание изменений для PR/ревью | PR-PATTERNS |
| ContextAgent | Сводка состояния проекта перед работой | PROJECT-CONTEXT |
| ArchReviewAgent | Проверка соответствия архитектурным решениям | ARCH-PATTERNS |
| DocsAgent | Синхронизация документации с кодом | DOCS-PATTERNS |

### Критерий «нужен ли агент в этой области»

Задай вопрос: если разные люди будут делать эту задачу без агента, результаты будут разными? Если да — агент нужен для стандартизации. Если нет — задача достаточно простая и агент только усложнит.

## 9. Типичные ошибки

### Ошибка 1: Размытая роль
```
# Плохо
## Роль
Помогает с кодом: находит проблемы, исправляет, пишет тесты и обновляет документацию.

# Хорошо
## Роль
Находит проблемы в Python-модулях и записывает их в структурированный отчёт. Не исправляет.
```

### Ошибка 2: Запреты написаны как рекомендации
```
# Плохо
## Правила
- Лучше не трогать файлы вне scope задачи
- Желательно не делать коммиты без проверки тестов

# Хорошо  
## Запреты
- НЕ открывать файлы вне target директории
- НЕ делать git commit если run_tests вернул failed > 0
```

### Ошибка 3: Скилл = пересказ документации
Агент уже знает общие принципы. Скилл про конкретный проект, не про программирование вообще.
```
# Плохо (общие знания)
## Правила
- Используй говорящие имена переменных
- Функции должны делать одно дело
- Пиши тесты

# Хорошо (специфика проекта)
## Правила
- Sentiment-анализатор использует словарный подход (не ML) — не предлагать замену
- D3-граф ожидает nodes[{id, label, weight}] — не менять структуру
- Все даты в UTC, отображение в локальном времени только в компонентах
```

### Ошибка 4: Агент без чёткого выхода
Если не описать формат выхода — каждый запуск даёт разную структуру. Следующий агент в цепочке не может надёжно парсить.

### Ошибка 5: Слишком много скиллов
Агент который читает 10 скиллов перед работой тратит весь контекст на чтение. 2-3 скилла — оптимум. Если нужно больше — скиллы слишком большие или роль агента слишком широкая.

### Ошибка 6: Скилл без антипаттернов
Агент знает как правильно, но не знает как выглядит неправильное. В реальном коде неправильное выглядит правдоподобно — иначе бы его не написали.

### Ошибка 7: Координатор исполняет
Координатор начинает «немного помогать» — сам исправляет мелкие вещи пока ждёт субагентов. Это нарушает схему: теперь непонятно кто за что отвечает и где искать изменения.

### Ошибка 8: Агент без запретов на WAL/коммиты
Каждый агент должен явно знать что он НЕ обновляет WAL и НЕ делает коммиты (если это не его роль). Иначе несколько агентов пишут в WAL одновременно.

## 10. Чеклист

### При создании агента

```
□ Роль — одно предложение, есть глагол и ограничение
□ Запреты написаны через "НЕ", а не "желательно не"
□ Указан точный формат выхода (не "markdown" а конкретная структура)
□ Скиллов не больше трёх
□ Описано взаимодействие: кто запускает, кому отдаёт
□ Агент не обновляет WAL (если это не его роль)
□ Агент не делает коммиты (если это не его роль)
□ Протестирован на реальной задаче, а не на примере
```

### При создании скилла

```
□ Написан для конкретного агента, не "вообще"
□ Есть антипаттерны, не только паттерны
□ Примеры из реального кода проекта, не абстрактные
□ Есть секция "Что НЕ входит в этот скилл"
□ Файл меньше 200 строк (если больше — разбить)
□ Нет пересказа общих принципов программирования
```

### При добавлении в систему

```
□ Агент добавлен в AGENTS.md (реестр агентов проекта)
□ Скиллы указаны в секции Скиллы агента
□ Описано взаимодействие с другими агентами
□ Протестирована цепочка: агент получает вход → пишет выход → следующий читает
□ Выход агента проверен на парсируемость (JSON валиден / Markdown структурирован)
```
