## ADR-001: Язык реализации — Python

**Дата:** 2026-02-26  
**Статус:** Принято  
**Связанные:** BOOT.md

### Контекст

Нужно выбрать язык для Qwenex. Рассматривались Go (как ralphex) и Python.

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Go** | Один бинарник, производительность, опыт ralphex | Нет MCP SDK, меньше AI-библиотек, медленнее прототипирование |
| **Python** | MCP SDK нативный, богатая AI-экосистема, быстрые итерации | Зависимости, медленнее Go, нет одного бинарника |
| **Гибрид (Go+Python)** | Go ядро + Python MCP | Сложнее деплой, два процесса, IPC overhead |

### Решение

**Выбрали Python (полностью)**

**Причины:**
1. **MCP SDK** — официальный SDK только для Python
2. **AI-экосистема** — LangChain, LlamaIndex, Ollama SDK из коробки
3. **Прототипирование** — быстрее итерации при разработке
4. **Интеграция с Qwen CLI** — сам Qwen CLI на Python, проще отладка
5. **Для CLI производительность не критична** — Go быстрее, но разница незаметна

**Последствия:**
- ✅ MCP нативный (не sidecar)
- ✅ Проще работа с AI-моделями
- ❌ Нужен venv/pip (не один бинарник)
- ❌ Нельзя переиспользовать код ralphex

## ADR-002: Архитектура MCP — один процесс

**Дата:** 2026-02-26  
**Статус:** Принято  
**Связанные:** BOOT.md

### Контекст

Как организовать MCP сервер: отдельный процесс (sidecar) или внутри Qwenex?

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Sidecar** | Разделение ответственности, независимые обновления | Два процесса, IPC overhead, сложнее деплой |
| **Один процесс** | Проще деплой, нет IPC, легче отладка | Меньше разделение ответственности |

### Решение

**Выбрали один процесс (MCP внутри `src/mcp/`)**

**Причины:**
1. **Проще деплой** — одна установка (`pip install qwenex`)
2. **Нет IPC overhead** — JSON-RPC через stdin/stdout не нужен
3. **Легче отладка** — один процесс, общие логи
4. **MCP — часть Qwenex** — не отдельный продукт

**Последствия:**
- ✅ `src/qwenex/` и `src/mcp/` в одном пакете
- ✅ Общий доступ к моделям данных, конфигурации
- ❌ Меньше модульности (но приемлемо для MVP)

## ADR-003: Гибридные субагенты

**Дата:** 2026-02-26  
**Статус:** Принято  
**Связанные:** BOOT.md

### Контекст

У Qwen CLI нет нативных субагентов (в отличие от Claude Code Task tool). Как эмулировать параллельное выполнение 5 агентов ревью?

### Рассмотренные альтернативы

| Вариант | Как работает | Плюсы | Минусы |
|---------|--------------|-------|--------|
| **Параллельные процессы** | 5 процессов Qwen CLI одновременно | Быстро | Ресурсоёмко (5x API вызовы) |
| **Последовательные запросы** | Один процесс, 5 запросов подряд | Экономно | Медленнее (5x время) |
| **Гибридный** | 2 параллельно + 3 последовательно | Баланс | Сложнее логика |

### Решение

**Выбрали гибридный подход**

**Схема:**
```
Фаза 1 (параллельно):
  - quality (критичный)
  - implementation (критичный)

Фаза 2 (последовательно):
  - testing
  - simplification
  - documentation
```

**Причины:**
1. **Критичные агенты параллельно** — quality + implementation самые важные
2. **Остальные последовательно** — экономят ресурсы
3. **Баланс** — 3 шага вместо 5, но быстрее чистого последовательного

**Последствия:**
- ✅ Быстрее чистого последовательного (~40% экономия времени)
- ✅ Меньше ресурсов чем чистый параллельный (2 процесса вместо 5)
- ⚠️ Сложнее логика (asyncio.gather + последовательный цикл)

**Реализация:**
```python
# Параллельно
critical_results = await asyncio.gather(
    run_agent("quality", session_id),
    run_agent("implementation", session_id)
)

# Последовательно
other_results = []
for agent in ["testing", "simplification", "documentation"]:
    result = await run_agent(agent, session_id)
    other_results.append(result)
```

## ADR-004: Модели — Qwen Cloud API (MVP) с заделом на расширение

**Дата:** 2026-02-26  
**Статус:** Принято  
**Связанные:** BOOT.md

### Контекст

Какие модели поддерживать в MVP? Только Qwen Cloud API или сразу локальные (Ollama) + другие провайдеры?

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Только Qwen Cloud** | Фокус на MVP, проще реализация | Нет локальных моделей, зависимость от API |
| **Qwen + Ollama сразу** | Локальные модели с начала | Больше работы, отвлечёт от ядра |
| **Мульти-провайдер (OpenAI, Anthropic)** | Гибкость | Значительно сложнее архитектура |

### Решение

**Выбрали Qwen Cloud API (MVP) с заделом на расширение**

**Архитектура:**
```python
class LLMProvider(Protocol):
    async def complete(self, prompt: str, **kwargs) -> str: ...
    async def check_health(self) -> bool: ...

class QwenCloudProvider(LLMProvider):
    # MVP реализация

class OllamaProvider(LLMProvider):
    # Задел на v0.2

class OpenAIProvider(LLMProvider):
    # Задел на v0.3
```

**Причины:**
1. **Фокус на MVP** — Qwen Cloud достаточно для начала
2. **Интерфейс LLMProvider** — легко добавить провайдера потом
3. **Конфигурация** — выбор провайдера через YAML config

**Последствия:**
- ✅ MVP быстрее (не тратим время на Ollama/OpenAI сразу)
- ✅ Легко расширить потом (интерфейс уже есть)
- ⚠️ Нет локальных моделей в MVP (но есть задел)

## ADR-005: BOOT/WAL/FEAT/PROP — глубокая интеграция

**Дата:** 2026-02-26  
**Статус:** Принято  
**Связанные:** BOOT.md

### Контекст

Как использовать систему документации BOOT/WAL/FEAT/PROP? Поверхностно (документация) или глубоко (интеграция)?

### Рассмотренные альтернативы

| Вариант | Описание | Плюсы | Минусы |
|---------|----------|-------|--------|
| **Поверхностная** | BOOT/WAL как документация для разработчиков Qwenex | Проще реализация | Нет уникальности |
| **Глубокая** | Qwenex читает BOOT.md, обновляет WAL.md, использует FEAT/PROP | Уникальное отличие, структурированный контекст | Сложнее реализация |

### Решение

**Выбрали глубокую интеграцию**

**Как работает:**
1. **BOOT.md** — Qwenex читает перед запуском (контекст проекта)
2. **WAL.md** — Qwenex обновляет после каждой задачи (прогресс)
3. **FEAT/PROP** — Qwenex читает как план выполнения
4. **MCP-инструменты** — `update_wal()`, `get_current_task()`, etc.

**Причины:**
1. **Уникальное преимущество** — нет аналогов у конкурентов
2. **Структурированный контекст** — AI понимает «почему», не только «что»
3. **WAL как прогресс-трекер** — человек видит статус в реальном времени
4. **REVIEW-маркеры** — human-in-the-loop по дизайну

**Последствия:**
- ✅ Qwenex обновляет WAL.md автоматически
- ✅ MCP предоставляет инструменты для работы с WAL
- ✅ AI читает BOOT.md для контекста
- ⚠️ Сложнее реализация (парсинг markdown, обновление)

## ADR-006: Git через subprocess

**Дата:** 2026-02-26  
**Статус:** Принято  
**Связанные:** BOOT.md

### Контекст

Как работать с git: использовать библиотеку (dulwich, go-git) или вызывать git CLI через subprocess?

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **dulwich (Python)** | Чистый Python, нет зависимостей | Меньше функциональности, сложнее отладка |
| **subprocess git** | Надёжно, все функции git, проще отладка | Зависит от установленного git |

### Решение

**Выбрали subprocess git**

**Причины:**
1. **Надёжность** — git CLI протестирован годами
2. **Отладка** — проще понять ошибку (git выводит понятные сообщения)
3. **Все функции** — worktrees, hooks, etc. из коробки
4. **git установлен везде** — стандартный инструмент разработчика

**Последствия:**
- ✅ `subprocess.run(["git", "worktree", "add", ...])`
- ✅ Зависимость от git CLI (но это стандарт)
- ❌ Нет кроссплатформенных проблем (git работает везде)

## ADR-007: REVIEW-маркеры

**Дата:** 2026-02-26  
**Статус:** Принято  
**Связанные:** BOOT.md

### Контекст

Как AI предлагает изменения в спеки? Менять напрямую или через маркеры?

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Прямые изменения** | AI сам меняет спеки | Риск неконтролируемых изменений |
| **REVIEW-маркеры** | AI предлагает, человек решает | Требует участия человека |

### Решение

**Выбрали REVIEW-маркеры**

**Формат:**
```markdown
<!-- REVIEW: [предложение] — причина: [почему] — ждёт: решения человека -->
```

**Причины:**
1. **Human-in-the-loop** — человек контролирует изменения
2. **Контекст сохраняется** — видно, почему предложено изменение
3. **Безопасность** — AI не меняет спеки молча

**Последствия:**
- ✅ AI пишет `<!-- REVIEW: Добавить кэширование — причина: ускорение -->`
- ✅ Человек читает, принимает/отклоняет
- ⚠️ Требует участия человека (но это фича, не баг)

## ADR-008: MVP без интеграции с dmux/cmux

**Дата:** 2026-02-26  
**Статус:** Принято  
**Связанные:** docs/COMPETITORS.md

### Контекст

Интегрировать ли с dmux/cmux сразу (MVP) или сделать самостоятельно, а интеграции добавить потом (v0.2)?

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Интеграция сразу** | Быстрее (dmux делает git/tmux), готовая мульти-агентность | Зависимость от dmux, сложнее отладка (2 процесса) |
| **Самостоятельно (MVP)** | Полный контроль, проще отладка, понимание проблем | Больше кода, велосипед |

### Решение

**Выбрали самостоятельно для MVP, интеграции в v0.2**

**Причины:**
1. **Прототипирование** — быстрее сделать простую версию самому
2. **Понимание** — лучше понять проблемы git/tmux оркестрации на себе
3. **Гибкость** — легче менять архитектуру на ранних этапах
4. **Нет блокировок** — не зависишь от dmux API/breaking changes

**План:**
- **MVP (недели 1-4):** Своя реализация (subprocess git, нет tmux)
- **v0.2 (недели 5-8):** Интеграция с dmux (параллельные сессии)
- **v0.3 (недели 9-12):** Интеграция с cmux (уведомления через OSC)

**Последствия:**
- ✅ MVP независимый
- ✅ Интеграции потом (не блокируют)
- ⚠️ Больше кода для MVP (но приемлемо)

## ADR-011: Анализ ralphex v0.18.0 и заимствование архитектуры

**Дата:** 2026-02-27  
**Статус:** Принято  
**Связанные:** BOOT.md, docs/COMPETITORS.md

### Контекст

ralphex v0.18.0 содержит реализацию worktree isolation и ensureGitIgnored. Нужно решить: интегрироваться в ralphex или заимствовать архитектуру для Qwenex.

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Интеграция в ralphex** | 40% работы, готовые тесты, web dashboard | Зависимость от upstream, merge конфликты, ограничения архитектуры |
| **Qwenex с нуля (Python)** | Полный контроль, MCP нативный, BOOT/WAL гибкость | 2x дольше (16-22 недели), писать тесты с нуля |
| **Гибрид (Go ядро + Python MCP)** | Переиспользование ralphex, MCP нативный | Сложнее деплой, два процесса, IPC overhead |

### Решение

**Выбрали Qwenex с нуля (Python)**

**Причины:**
1. **BOOT/WAL/FEAT/PROP** — уникальное преимущество, сложно интегрировать в ralphex
2. **MCP сервер** — нативный Python проще чем Go+Python гибрид
3. **Трансформация планов** — AI-фича, проще реализовать на Python
4. **Локальные модели** — Ollama интеграция проще на Python
5. **Независимость** — нет рисков от upstream ralphex

**Что заимствуем из ralphex:**
- ✅ **Worktree isolation концепция** — git worktree для изоляции задач
- ✅ **ensureGitIgnored логика** — авто-добавление паттернов в .gitignore
- ✅ **5-агентное ревью** — гибридное выполнение (2 параллельно + 3 последовательно)
- ✅ **Web dashboard концепция** — real-time мониторинг прогресса
- ✅ **VCS абстракция** — поддержка разных VCS через конфигурацию

**Что НЕ заимствуем:**
- ❌ **Код** — пишем свой на Python (нет копирования)
- ❌ **Зависимости** — свой pip install (не go modules)
- ❌ **CI/CD** — свой pipeline (не GitHub Actions ralphex)
- ❌ **Структура** — своя организация проекта

**Архитектурные параллели:**

```
ralphex (Go)                          Qwenex (Python)
├── cmd/ralphex/main.go              ├── src/qwenex/cli.py
├── pkg/executor/                    ├── src/qwenex/orchestrator.py
├── pkg/git/service.go               ├── src/qwenex/git_wrapper.py
├── pkg/config/                      ├── src/qwenex/config.py
├── pkg/progress/                    ├── src/qwenex/progress.py
├── pkg/web/dashboard.go             ├── src/qwenex/dashboard.py (задел)
└── pkg/mcp/ (нет)                   └── src/mcp/server.py ✅ Уникальное
```

**Последствия:**
- ✅ Полный контроль над архитектурой
- ✅ MCP сервер нативный (Python SDK)
- ✅ BOOT/WAL/FEAT/PROP без компромиссов
- ❌ 2x дольше до MVP (16-22 недели vs 8-12)
- ❌ Нужно писать тесты с нуля (80% покрытие)
- ❌ Наступим на свои грабли (ralphex уже решил проблемы)

**Митигация рисков:**
- Тесты с первого дня (pytest, 80%+ покрытие)
- Заимствование архитектуры (не изобретать велосипед)
- Документирование решений (ADR, BOOT, WAL)
- Постепенная разработка (MVP → v0.2 → v0.3)

## ADR-014: Гибридное ревью (2+3) — требуется исследование

**Дата:** 2026-02-27  
**Статус:** Требуется исследование  
**Связанные:** ADR-003, FEAT-002

### Контекст

В ADR-003 принято решение о гибридном выполнении ревью:
- 2 агента параллельно (quality, implementation)
- 3 агента последовательно (testing, simplification, documentation)

**Проблема:** ralphex запускает все 5 агентов параллельно через Claude Task tool. Qwenex будет медленнее.

### Требуется исследование

**Вопрос:** Почему именно гибридный подход, а не все 5 параллельно?

**Возможные причины:**
1. **Qwen CLI не поддерживает Task tool** — нет нативной параллельности
2. **Ресурсные ограничения** — 5 параллельных процессов = 5x API вызовов одновременно
3. **API rate limits** — Qwen API может лимитировать параллельные запросы

### План исследования

1. Проверить, поддерживает ли Qwen CLI Task tool (аналог Claude Code)
2. Протестировать 5 параллельных процессов Qwen CLI
3. Измерить:
   - Время выполнения (параллельно vs гибридно)
   - API cost (параллельно vs гибридно)
   - Rate limit ошибки

### Критерии пересмотра

**Перейти на полностью параллельное (5 агентов), если:**
- Qwen CLI поддерживает Task tool ИЛИ
- 5 параллельных процессов стабильны (нет rate limit) И
- Время выполнения критично (пользователи жалуются)

**Оставить гибридное (2+3), если:**
- Qwen CLI не поддерживает Task tool И
- 5 параллельных процессов вызывают rate limit ИЛИ
- Resource usage неприемлем (5x память/CPU)

### Временное решение (MVP)

**Гибридное (2+3) для MVP**, пересмотреть в v0.2 после исследования.

## ADR-015: Agentic RAG термин — уточнение

В ARCHITECTURE.md использован термин "Agentic RAG" для описания архитектуры Qwenex.

### Обновлённая терминология

|---------------|--------------|

## ADR-017: Qwen CLI интерфейс — спецификация для FEAT-001

**Дата:** 2026-02-27  
**Статус:** Принято  
**Связанные:** FEAT-001

### Контекст

Нужно явно описать, как Qwenex запускает Qwen CLI.

### Решение

**Интерфейс:** subprocess с stream-json output

**Команда:**
```bash
qwen --yolo --output-format stream-json --prompt "<task>"
```

**Аргументы:**
- `--yolo` — аналог `--dangerously-skip-permissions` в Claude Code
- `--output-format stream-json` — streaming JSON для парсинга
- `--prompt` — задача из плана

**Парсинг output:**
```python
# src/qwenex/qwen_executor.py
async def run_task(self, prompt: str):
    process = await asyncio.create_subprocess_exec(
        "qwen",
        "--yolo",
        "--output-format", "stream-json",
        "--prompt", prompt,
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE
    )
    
    # Парсинг streaming JSON
    async for line in process.stdout:
        event = json.loads(line)
        if event["type"] == "assistant":
            yield event["message"]["content"][0]["text"]
```

**Таймауты:**
- Max 10 минут на задачу
- Graceful shutdown по SIGINT

## ADR-018: Процесс обновления WAL.md — гибридный подход

**Дата:** 2026-02-27  
**Статус:** Принято  
**Связанные:** BOOT.md, FEAT-003 (MCP сервер)

### Контекст

WAL.md — оперативная память проекта. Нужно определить, кто и как обновляет WAL.

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **AI автоматически** | Актуальный WAL, нет ручного труда | AI может ошибиться в приоритетах, нужен MCP инструмент |
| **Человек вручную** | Человек контролирует приоритеты | Ручной труд, WAL может устареть |
| **Гибридный** | Баланс контроля и автоматизации | Сложнее реализация |

**Гибридный подход с возможностью выбора опций:**

**Автоматически (AI):**
- Начало сессии (S-NNN → S-NNN+1)
- Завершение задачи (✅ Завершено)
- История сессий (📜 История)
- Фиксация изменений документации

**Человек:**
- Выбор следующей задачи (⚡ Текущая задача)
- Утверждение изменений перед коммитом
- Изменение приоритетов в очереди

**MCP инструменты (для AI):**
```python
# src/mcp/tools/wal.py
class WALTools:
    async def start_session(self) -> str:
        """Начать новую сессию (S-NNN → S-NNN+1)"""
        
    async def complete_task(self, task_id: str, notes: str) -> str:
        """Отметить задачу завершённой"""
        
    async def log_change(self, type: str, description: str) -> str:
        """Зафиксировать изменение (код, документация, тесты)"""
        
    async def add_question(self, question: str, category: str) -> str:
        """Добавить открытый вопрос"""
        
    async def end_session(self) -> str:
        """Завершить сессию, обновить историю"""
```

**Фиксация изменений документации:**

Все изменения в docs/ фиксируются в WAL.md:

- [x] **[DOC-002: Анализ RAG.txt]** — Добавлен Agentic RAG паттерн · 2026-02-27

**Связь с коммитами:**

```bash

- Added MCP tools for WAL updates
- Fixes WAL.md #3"
```

### Последствия

- ✅ WAL.md всегда актуален
- ✅ Человек контролирует приоритеты
- ✅ Автоматическая фиксация изменений
- ⚠️ Нужны MCP инструменты для WAL
- ⚠️ AI может ошибиться (нужна валидация человеком)

## ADR-019: Два режима работы — автономный и интерактивный

**Дата:** 2026-02-27  
**Статус:** Принято  
**Связанные:** FEAT-001, RISK-005

### Контекст

Позиционирование «автономное выполнение» требует постоянного human-in-the-loop через REVIEW-маркеры. Пользователь не знает, когда можно отвлечься.

### Рассмотренные альтернативы

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Один режим** | Проще реализация, понятнее | Нет гибкости |
| **Два режима** | Гибкость, явный UX | Сложнее реализация |
| **Режимы через флаги** | Явно в CLI, скрипты | Больше аргументов |

### Решение

**Два режима с явными флагами CLI**

**Режимы:**
- **`--auto`** — автономный, REVIEW-маркеры авто-утверждаются
- **`--interactive`** — интерактивный, пауза на REVIEW-маркерах

**Реализация:**
```python
# src/qwenex/cli.py
if args.auto:
    review_mode = ReviewMode.AUTO  # REVIEW авто-утверждаются
elif args.interactive:
    review_mode = ReviewMode.INTERACTIVE  # Пауза на REVIEW
```

**Причины:**
1. **Явный UX** — пользователь знает, чего ожидать
2. **Гибкость** — разные сценарии (ночь vs день)
3. **Скрипты** --auto для CI/CD

**Последствия:**
- ✅ Прозрачный UX
- ✅ Гибкость для разных сценариев
- ⚠️ Сложнее реализация (два режима)
