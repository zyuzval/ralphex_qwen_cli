## Шаг 2 — Единицы знания

```

[КЗ-001] Парадокс автономности vs контроля в AI-оркестраторах

Тип     : инсайт

Контекст: Проект позиционируется как "автономное выполнение", но требует постоянного human-in-the-loop через REVIEW-маркеры

Суть    : Qwenex попадает в ловушку промежуточной категории: не полностью автономен (как ralphex), не полностью интерактивен (как Aider). Это создаёт неопределённость в UX — пользователь не знает, когда можно отвлечься, а когда нужно быть на связи

Когда   : При проектировании AI-инструментов с элементами автономности

Когда ≠ : Когда целевая аудитория чётко хочет либо "нажал и забыл", либо "помоги мне писать код"

Блок    : [Б-1]

```

```

[КЗ-002] Риск оптимизации без данных в гибридном ревью

Тип     : инсайт

Контекст: Принято архитектурное решение о гибридном выполнении 5 агентов (2 параллельно + 3 последовательно) без измерений производительности

Суть    : Архитектурное решение принято на основе предположения о "балансе скорости и ресурсов", но нет данных: неизвестны rate limits Qwen API, неизмерено время параллельного vs последовательного выполнения. Это преждевременная оптимизация, которая может привести к ненужной сложности без выигрыша

Когда   : При выборе между параллельным и последовательным выполнением в распределённых системах

Когда ≠ : Когда есть чёткие бенчмарки или ограничения ресурсов известны заранее

Блок    : [Б-1]

```

```

[КЗ-003] Technical debt как архитектурный компромисс

Тип     : модель

Контекст: MCP сервер спроектирован в одном процессе с Qwen CLI, что создаёт single point of failure, но отложено "на v0.2"

Суть    : Классификация "technical debt" маскирует фундаментальный архитектурный риск. Если Qwen CLI нестабилен (а это новый инструмент), весь продукт ненадёжен. Это не "долг", а "ставка на стабильность внешней зависимости"

Когда   : При оценке рисков архитектурных решений, отложенных на будущее

Когда ≠ : Когда рефакторинг действительно не критичен для MVP и есть путь миграции

Блок    : [Б-1]

```

```

[КЗ-004] Проблема масштабирования документации

Тип     : инсайт

Контекст: Система BOOT/WAL/FEAT/PROP требует постоянного обновления WAL.md, создавая циклическую зависимость: MCP сервер обновляет WAL, который описывает MCP сервер

Суть    : Сложность поддержания документации может превысить пользу от неё. Система спецификаций создаёт мета-работу (обновление статусов, сессий, ADR) вместо работы над продуктом. Возможно, WAL.md должен быть автогенерируемым из git history

Когда   : При проектировании систем документации для AI-инструментов

Когда ≠ : Когда команда большая и документация критична для координации

Блок    : [Б-1]

```

```

[КЗ-005] Неуникальность MCP как конкурентное преимущество

Тип     : инсайт

Контекст: MCP позиционируется как ключевая фича, но это industry trend 2026

Суть    : MCP — не "moat" (защитный ров), а "table stakes" (базовая ставка). Конкуренты (ralphex, Cline) могут добавить MCP за 2-3 недели. Реальная уникальность — в системе спецификаций, но она требует обучения пользователей и создаёт friction

Когда   : При оценке конкурентных преимуществ на основе стандартов/протоколов

Когда ≠ : Когда есть экосистема инструментов, которые сложно воспроизвести

Блок    : [Б-1]

```

```

[КЗ-006] Риск позиционирования против более зрелого конкурента

Тип     : инсайт

Контекст: 60% архитектуры заимствовано из ralphex, но разработка занимает 16-22 недели против 8-12 для интеграции

Суть    : Если ralphex добавит спецификации и MCP, преимущество Qwenex исчезнет, а у ralphex уже есть рабочий продукт. Конкуренция должна быть не на функциях, а на экосистеме — но Qwen CLI слабее Claude Code

Когда   : При выборе между форком/интеграцией и разработкой с нуля

Когда ≠ : Когда уникальные фичи действительно невозможно добавить в существующий продукт

Блок    : [Б-1]

```

```

[КЗ-007] Парадокс трансформации планов

Тип     : инсайт

Контекст: Фича "человек пишет просто → AI превращает в FEAT/PROP" отложена на v0.2, но вся система спецификаций требует дисциплины

Суть    : Цикл "простой план → AI-генерация → human review → возможно переписывание" может быть медленнее, чем сразу писать FEAT/PROP. Фича решает проблему, которую сама создаёт (сложность спецификаций)

Когда   : При проектировании AI-фич, упрощающих работу с собственной сложностью системы

Когда ≠ : Когда входной формат значительно проще и целевая аудитория не хочет учить новый формат
```

```
[КЗ-008] Необходимость прототипирования критической зависимости

Тип     : решение

Когда   : Когда проект зависит от внешнего инструмента с неполной документацией

Когда ≠ : Когда внешний инструмент зрелый и хорошо документирован
```

## Шаг 5 — Мета-наблюдение

**Нестандартный угол:** Ревью выявило фундаментальное противоречие в философии проекта. Qwenex пытается построить "автономный оркестратор" вокруг концепции, которая требует постоянного человеческого внимания (спецификации, REVIEW-маркеры, обновление WAL). Это не автономность в классическом смысле, а "structured autonomy" — автономность в рамках строгого протокола. 

Интересно, что сама система спецификаций (BOOT/WAL/FEAT/PROP), позиционируемая как уникальное преимущество, создаёт мета-работу, которая может превысить пользу от автоматизации. Проект борется с собственной сложностью, предлагая AI-трансформацию планов как решение — но это решение проблемы, которую сама система создаёт.

Самый ценный инсайт — в переосмыслении категории "technical debt" в ADR-016: то, что названо "долгом", на самом деле является "ставкой на стабильность внешней зависимости". Это не долг, который можно вернуть, а архитектурный риск, который либо сработает, либо убьёт проект.
